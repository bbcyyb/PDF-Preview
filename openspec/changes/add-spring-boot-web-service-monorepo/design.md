## 背景

仓库当前在根目录承载一个 React + TypeScript + Vite 单页应用。现有应用负责 PDF/OCR 固定样例展示、坐标映射和 UI 测试。本次变更需要在保留当前前端行为的同时新增后端，因此实现上既需要迁移仓库布局，也需要新增一个服务端应用。

## 目标与非目标

**目标：**
- 将仓库拆分为 monorepo，并用 `frontend/` 和 `backend/` 清晰分离两个应用。
- 将现有前端迁移到 `frontend/` 后，保留 PDF/OCR 行为、测试、固定样例、前端文档和构建流程。
- 在 `backend/` 下新增 Java 17 Spring Boot 后端。
- 暴露一个可自动化测试的最小 Hello World HTTP API。
- 提供根目录脚本或文档，让新的运行、测试和构建命令易于发现。

**非目标：**
- 不连接前端和后端。
- 不把固定样例加载、OCR 映射或 PDF 渲染迁移到后端。
- 不新增持久化、认证、上传流程或部署自动化。
- 不改变现有 PDF/OCR 用户可见行为。

## 决策

1. 使用 `frontend/` 和 `backend/` 作为一级应用目录。
   - 理由：这些名称常见、明确，并能让职责边界直观可见。
   - 替代方案：`apps/web` 和 `apps/api`。这种布局更适合大量应用扩展，但会给当前项目增加暂时不需要的间接层。

2. 迁移 React + Vite 应用到 `frontend/` 时保持其内部结构尽量完整。
   - 理由：前端已有可工作的 TypeScript、Vitest、Vite、固定样例和 PDF 资源约定。以最少内部变更完成迁移可以降低回归风险。
   - 替代方案：在新布局下重新创建前端包。这会增加代码扰动，但不会带来请求能力上的变化。

3. 后端使用 Java 17 + Spring Boot + Maven。
   - 理由：Spring Boot 直接满足请求的后端技术栈，当前开发环境已具备 Maven 和 Java 17，可以在本地完成可靠验证。
   - 替代方案：Gradle。Gradle 同样适用于 Spring Boot，但当前环境没有可用的 Gradle 安装或 wrapper，使用 Maven 更直接。

4. 将 Hello World API 设计为 `/api/hello` 下的专门 REST 端点。
   - 理由：`/api` 前缀为后端端点保留清晰命名空间，并避免与前端路由或静态资源冲突。
   - 替代方案：根级 `/hello`。实现更简单，但未来增加更多后端端点时扩展性较差。

5. 保持前端和后端验证命令相互独立。
   - 理由：两个应用使用不同工具链。独立命令更容易定位失败原因，并避免过早耦合 Node 和 Java 构建生命周期。
   - 替代方案：一个总是运行所有检查的根目录命令。后续可以添加，但不应掩盖应用边界。

## 风险与取舍

- 仓库迁移破坏相对路径或固定样例 URL -> 在 `frontend/public/` 下保留前端公开资源结构，将前端专用的 `docs/`、`fixtures/`、`dist/` 归入 `frontend/` 边界，并只更新依赖根目录位置的路径。
- 现有开发命令发生变化 -> 更新根目录和应用文档，明确列出前端/后端命令。
- 不同机器上的后端工具链可用性不同 -> 将 Java 17 和 Maven 作为必需工具链，并通过标准 Maven 项目结构降低环境差异。
- 根目录包元数据可能变得含糊 -> 将根目录视为工作区编排层，应用依赖保留在各自目录中。

## 迁移计划

1. 创建 `frontend/`，并将现有 Vite 包、源码、固定样例、前端文档、测试和配置迁移进去。
2. 新增或更新根目录包元数据/脚本，将前端命令委托给 `frontend/`。
3. 创建 `backend/`，包含 Java 17 Spring Boot 应用、Maven 构建、控制器和自动化测试。
4. 更新 README/AGENTS 或项目文档，确保新命令和目录布局准确。
5. 运行前端类型检查/测试/构建、后端测试/构建和 OpenSpec 校验。

回滚方式是在发布前对 monorepo 迁移和后端新增内容做仓库级 revert；本次变更不涉及持久化数据或运行时迁移。
